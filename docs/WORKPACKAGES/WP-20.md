after WP-8 and WP-13 as `feat/WP-20b-deploy-refresh`). Milestone S-M1
(first deploy), S-M6. Owns `deploy/compose/` (beyond WP-0's skeleton),
`deploy/caddy/`, `deploy/ENV.md`, `deploy/staging/` (the only place a

## What to build

- `deploy/compose/docker-compose.yml` completed: resource limits that
  fit the droplet share for this system (the seven Go processes ≈ 64–256
  MB each, NATS 256 MB, PostgreSQL 512 MB, TimescaleDB 768 MB, web 256
  MB; documented), healthchecks per service with the `/readyz`
  semantics (a `degraded` service is healthy for compose, a `down`
  one is not), restart policies, named volumes, log rotation, NATS
  config with accounts per process and JetStream storage limits,
  PostgreSQL and TimescaleDB tuning for the memory share, `.env.example`
  with every `USSP_*` variable and a comment; profiles `demo` (adds the
  InterUSS DSS by digest, the lab fakes binary, a geoid grid download
  step into a volume) and `conformance` (WP-19 fills).
- `deploy/caddy/ussp.caddy`: an importable snippet with `{$USSP_HOST}`
  routing `/v1/telemetry*` → `telemetry-ingest`, `/v1/traffic*` and
  `/v1/alerts` (WS) → `traffic-ws`, `/uss/flights*`,
  `/uss/identification_service_areas/*`, `/v1/authority/*` → `rid-sp`,
  everything else under `/v1`, `/uss/v1`, `/oauth`, `/.well-known` →
  `api`, `/_bff/*` and the rest → `web`; rate limits per path group;
  WebSocket timeouts; headers (HSTS, no-sniff); the snippet is imported
  by the owner's shared Caddyfile in the private infra repo.
- `deploy/ENV.md`: every variable with process, default, unit, example,
  and whether it is a secret (secrets come from the droplet's env file,
  never the repo).
- CI `image` job: on `main` and tags, build both images with
  `docker/build-push-action`, tag `sha-<short>` and the git tag, push to
  GHCR, generate an SBOM (`syft`) and sign with `cosign` keyless; on
  pull requests build only. Cache with GHA cache.
- Runbooks: `deploy.md` (pull by digest, `docker compose up -d`,
  migrations run by `api`/`tsdb-writer` at start and how to watch them,
  the first-run `start` operating-status notice from the console,
  smoke checks: `/readyz` of every process, one simulated operator from
  the lab filing an intent), `rollback.md` (previous digest, migration
  compatibility rule: a release never drops a column the previous
  release reads; `down` migrations tested in CI), `backup.md` (nightly
  `pg_dump` of the relational database, Timescale chunk export of the
  last 7 days, both to the backup account; restore rehearsal steps and
  a `verify` that counts rows), `teardown` instructions whose success
  path is verified (the script lists what remains and exits 0 only when
  nothing does).

## Done when

- [ ] `make compose-up` with the `demo` profile on a laptop brings up
  the stack healthy; a simulated operator from the lab (or the fakes)
  files an intent and streams telemetry through Caddy's local
  equivalent (a local Caddy with a self-signed cert in the profile);
  `make compose-down` verifies and exits 0.
- [ ] Images published on `main` with SBOM and signature; `cosign
  verify` documented and run once in CI as a check.
- [ ] Backup and restore rehearsed once locally and recorded in the
  runbook with the row counts.
- [ ] Memory of the whole stack on a 2 vCPU / 3.8 GB VM measured at idle
  and with 100 simulated drones and written in `deploy/ENV.md`
  (the share this system may take beside the other four).
- [ ] No hostname outside `deploy/staging/` (CI check from WP-0 passes);
  `CHANGELOG.md`; PR with the measurements.

## Safety notes

- The deploy is the owner's act; this WP never runs it. The runbook
  says so on its first line.
- A backup that reports success must have counted what it wrote
  (E-02); a restore that was never rehearsed is not a backup.
