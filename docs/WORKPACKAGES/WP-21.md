# WP-21: InterUSS test interfaces

Branch `feat/WP-21-interuss-test-interfaces`. Milestone S-M6. Approved
by the owner on 2026-10-05 as the answer to PLAN §15 Q34. Owns
`cmd/test-interfaces`, `internal/testif/`, `api/standards/interuss/`
(the pinned InterUSS automated-testing interface files and their
generated server code under `internal/stdapi/interuss/`), the image
target `uspace-ussp-testif`, the conformance profile's `test-interfaces`
service and the `uss_qualifier` steps of `scripts/conformance.sh` and
the `conformance` workflow, `deploy/conformance/test-operator.yaml`,
`docs/RUNBOOKS/WP-21.md`. Depends on WP-9 (rid-sp), WP-13 (the F3548
USS endpoints and the DSS writer), WP-19 (the conformance hook and the
lab's suite), and on two things outside this repository, listed under
"Blocked by". Consumers: the lab's suite (`uspace-lab` WP-L7, L-M4),
GCAA (Q13: `uss_qualifier` F3411 SP and F3548 SCD as a certification
condition).

The one-line design: **a test-only process that is an operator client
of this USSP's published API and nothing else.** `uss_qualifier` drives
the InterUSS interfaces; the process turns each injected flight into
telemetry on `WS /v1/telemetry` and each flight plan into an intent on
`POST /v1/intents`, with an operator credential, exactly as the lab's
simulated operator does. `telemetry-ingest`, `rid-sp`, `api`'s intent
service, the deconfliction, the DSS writer and the ISA worker neither
know nor care that the operator is a test. There is no test flag on a
judgement, no test branch in a safety package, and the production image
does not contain the process.

## What to build

### The process: `cmd/test-interfaces` (`ussp-test-interfaces`)

- One listener, `USSP_TEST_INTERFACES_ADDR` (default `:8087`), serving
  the InterUSS automated-testing interfaces under one base path:
  `/test/rid/v1/injection/*`, `/test/rid/v1/observation/*`,
  `/test/flight_planning/v1/*`. Nothing else is served there but
  `/healthz`, `/readyz` and `/metrics`. The lab Caddy of the conformance
  stack routes `/test/*` to it; the production Caddy snippet
  (`deploy/caddy/ussp.caddy`) never does, and a test that reads the
  snippet asserts it (E-01's twin: the conformance overlay's Caddy
  config routes it, and the same test asserts that).
- **Refused unless enabled.** The process starts only with
  `USSP_TEST_INTERFACES=on` and a `USSP_SYSTEM_ID` containing `TEST` or
  `DEV` (the WP-19 rule, now enforced by the binary and not only by the
  hook); otherwise it exits 2 with a message naming both, before any
  listener is opened. `on` is printed at error level in every status
  period, as `USSP_MTLS_MODE=off` is (M25). The production compose does
  not define the service; `deploy/compose/docker-compose.yml` is tested
  to name no `test-interfaces` service and no `uspace-ussp-testif`
  image.
- **Not in the production image.** The binary is built as a separate
  image target `ghcr.io/rootxkit/uspace-ussp-testif:<sha>` (a stage of
  `deploy/Dockerfile`, pushed by the `image` job like the web image,
  SBOM and cosign the same). `ghcr.io/rootxkit/uspace-ussp:<sha>` does
  not contain it; the image job checks that the production image has no
  `ussp-test-interfaces` entrypoint. `cmd/ussp-dev` runs it in-process
  only with the switch on.
- **A client, not a system.** `internal/testif` imports `config`, `obs`,
  `httpx`, the generated national client (`internal/national/client`),
  the generated InterUSS server interfaces
  (`internal/stdapi/interuss/`), `uspace-core/f3411` and `f3548` for
  the wire types, and nothing from `telemetry`, `flights`, `ridsp`,
  `intent`, `dss`, `conformance`, `traffic`, `store` or `bus`
  (`scripts/check-deps.sh` adds the rule). It opens no database and no
  NATS connection. It reaches the USSP the way an operator does: the
  USSP's base URL (`USSP_TEST_INTERFACES_USSP_BASE_URL`), an operator
  machine client of the USSP's own issuer
  (`USSP_TEST_INTERFACES_OPERATOR_CLIENT_ID`, `_SECRET_FILE`; scopes
  `ussp.telemetry`, `ussp.intents`, `ussp.traffic`) and a portal session
  of the test operator's `operator_admin` for the serial bindings
  (`USSP_TEST_INTERFACES_SESSION_FILE`; the alternative, binding every
  serial of the pool at seed time, is chosen if the first run shows the
  injected serials are not knowable in advance, and recorded). Every
  value is documented in `deploy/ENV.md` with `by: test-interfaces`.

### Auth on the test listener

- Tokens are verified by the same `core/auth.Verifier` with the same
  issuer list and `USSP_AUDIENCES` (M18): in the lab, the lab issuer
  and `lab-01`. The scopes the interfaces name are **not catalogue
  scopes** and never become one: `rid.inject_test_data`,
  `dss.read.identification_service_areas`,
  `interuss.flight_planning.direct_automated_test`,
  `interuss.flight_planning.plan` (and `utm.inject_test_data` if scd v1
  is built) live in `internal/testif/scopes.go` as the test listener's
  closed list, taken from the pinned files' `security` blocks by a test
  that reads them (as WP-3's test reads F3548's). `internal/auth.
  EcosystemScopes` is unchanged, so an `api`, `rid-sp`, `telemetry-ingest`
  or `traffic-ws` route that named one of them would fail
  `ValidateAccess` at start (test: it does). Without a credential 401,
  another scope 403, with the problem body; counted
  (`testif_refused_no_token`, `testif_refused_scope`, ...).
- The process holds the test operator's credential and session, both
  from files, never from the environment or a command line; the
  conformance stack's `gen-secrets.sh` step writes them into
  `local/conformance/state/` (git-ignored).

### RID injection → the production Service Provider path

`PUT /test/rid/v1/injection/tests/{test_id}` with `CreateTestParameters
{requested_flights[]}`:

1. Validate the body with the generated types; refuse what the file
   refuses (400 with the InterUSS error body).
2. For each `TestFlight`: take its `uas_id` (the serial, or one from the
   fixture pool when the injection carries none), bind it to the test
   operator's client through `POST /v1/accounts/operators/{id}/clients/{id}/serials`
   if it is not bound (the real binding path, F8 validity included), and
   open one `WS /v1/telemetry` session per flight (or one shared
   session; the ingest's per-client 2 Hz cap and `MaxBatchFrames` are
   read, not assumed, and the choice recorded).
3. Replay the flight's `telemetry[]` **at its timestamps**: each
   `RIDAircraftState` becomes one `telemetry/v1` frame (`ts` = the
   state's `timestamp`, `position`, `alt_wgs84_m` from `position.alt`
   (W84 as the file says), `height_m`/`height_ref` from `height`,
   `speed_ms`, `track_deg`, `vspeed_ms`, `status`
   (`operational_status`), `accuracy_h`, `accuracy_v`,
   `timestamp_accuracy_s`, `operator_position` from the first
   `details_responses[].details.operator_location`), sent when the
   wall clock reaches `ts` (a state in the past is sent at once with
   `backlog: true`, which the ingest places as history: the suite then
   sees exactly what a late operator would get). The last state is
   followed by a frame with `end: true`. Nothing is mapped from memory:
   every member name comes from the generated types on both sides, and
   the mapping test round-trips the lab's `tbilisi_flights_data` shape.
4. Answer `ChangeTestResponse {injected_flights[]}` with each flight's
   `injection_id` and the USSP's own flight id once the ingest has
   acknowledged the first frame (the `status` frame's `accepted`), and
   the test's `version`. A frame the ingest refuses (an unbound serial,
   a disabled source, a teleport) makes the injection fail with the
   ingest's reason in the InterUSS error body: the test process never
   retries past a refusal, never rewrites a sample to make it pass.
5. `DELETE /tests/{test_id}` ends every session of the test (an `end`
   frame, then the close) and answers once `telemetry-ingest` has
   acknowledged it; the ISA deletion is the ISA worker's, observed by
   the suite in the DSS, not performed here.
6. `GET /user_notifications` answers the empty list the file allows
   when the USSP has no user-facing notification to report; the first
   run says whether the suite asks for more.

What the suite then observes (through the mock DP and the lab DSS) is
`rid-sp`'s `GET /uss/flights`, `/details` and the ISA the `api` ISA
worker wrote: the production path end to end, with the only difference
from a real operator being who holds the credential. `details` serve
what the USSP knows: `operator_id` from the binding's registration,
`uas_id.serial_number` from the serial, `operator_location` from the
telemetry, `operation_description` from the authorisation. The injection's
`details_responses` are **not** served back; if the suite compares a
member the USSP derives differently from the injected text, that is a
finding for the owner (recorded in the runbook and in PLAN §15.2 as a
new question), never a shortcut that serves injected text past the
registry.

### flight_planning v1 → the production intent path

- `GET /status`: `Ready` with the USSP's `/readyz` summary; `NotReady`
  (as the file spells it) while the USSP's `api` is not ready.
- `PUT /flight_plans/{flight_plan_id}` (`UpsertFlightPlanRequest`):
  the `FlightPlan` maps onto `intent/request/v1`:
  `basic_information.area[]` (Volume4D, W84) → `volumes`;
  `astm_f3548_21.priority` → `priority`, with `flight_type =
  special_operation` when the priority is above the policy's normal
  (the mapping the policy row defines, INV-03);
  `uspace_flight_authorisation` → `uas_serial`, `operator_reg`
  (`operator_id`), `category` (`operation_category`), `mode`
  (`operation_mode`), `class_label` (`uas_class`),
  `identification_technology` (`identification_technologies`),
  `type_certificate`, `connectivity_methods`, `endurance_s`
  (`endurance_minutes` × 60), `loss_of_c2_procedure`
  (`emergency_procedure_url`); `basic_information.usage_state` and
  `uas_state` → the intent's action (`Planned` → file; `InUse` → file
  then `PATCH activate`; a plan already filed → `PATCH modify`; a
  `uas_state` of `Contingent` or `OffNominal` is **reported, not
  acted on**: the USSP's own conformance monitor judges the state from
  telemetry, and the response says the state was not taken from the
  plan). The Annex IV items the file does not carry (`contingency`,
  `emergency_contact_ref`, `pilot_ref`, `takeoff`, `landing`) come from
  `deploy/conformance/test-operator.yaml`, never from code (pending
  GCAA: the fixture is the lab's reading of Annex IV for a test
  operator).
- The decision maps onto `PlanningActivityResult` and `FlightPlanStatus`
  from the decision the intent service made: `authorised` /
  `accepted_voluntary` → `Completed`, `Planned` or `OkToFly`; `rejected`
  → `Rejected` with the refusal's `conflicts[]` in `notes`; a validation
  refusal (an invalid serial by `core/serial`, a missing item, a volume
  the USSP cannot place) → `Rejected`; `pending_dss` →
  `Failed` with the problem's `detail` (the suite must see that the DSS
  was not written, not a pretend success); `pending_validation` and
  `pending_authority` → `Failed` naming the state. The mapping is a
  table in `internal/testif/plan.go` with a test per row (E-01: every
  `Rejected` row has its `Completed` twin).
- `DELETE /flight_plans/{id}` → `PATCH {action: end}` and the intent's
  end state; `POST /clear_area_requests` ends every intent of the test
  operator whose volumes intersect the area (through `GET /v1/intents`
  and `PATCH`), answering what was ended and what could not be, each
  with its reason.
- The F3548 side the suite then observes, the operational intent
  reference in the lab DSS with its ovn, the notification to the mock
  USS, the conflict with the mock USS's intent, the priority preemption,
  is `api`'s intent service, `internal/intent/deconflict` and the DSS
  writer, unchanged. A check the suite fails is a finding in those
  packages (a `fix(...)` PR naming the check, as WP-19 did), or a spec
  gap for the owner; it is never a branch in `testif` that answers
  what the suite wants.

### RID observation (informative)

`GET /test/rid/v1/observation/display_data?view=` and
`/display_data/{id}` serve what the USSP's Display Provider role shows
a person: `traffic-ws`'s `GET /v1/traffic/snapshot?bbox=` with the test
operator's `ussp.traffic` credential, the tracks with `trust: provider`
(the peers' flights read through the DSS and `GET /uss/flights`, WP-14)
mapped onto `observation.yaml`'s `GetDisplayDataResponse` (positions,

authority is the national Display Provider; this hook exists so the lab

second observer. It serves no more than a staff console would.

## Safety notes

- Nothing here can reach an aircraft: the process holds an operator
  client's credential of this USSP and speaks to this USSP; the
  telemetry socket carries only `status` frames back, as for any
  operator (hard rule 1).
- The process never answers for a judgement. A flight plan's result is
  the intent service's decision; an injected flight is what `rid-sp`
  serves from the ingest. The suite failing on a real behaviour is the
  point of the suite; a `testif` change that makes a check pass by
  reading or serving injected data in place of the USSP's is a review
  failure (T12, INV-03).
- Never in production: not in the production image, not in the
  production compose, not in the Caddy snippet, refused by the binary
  without the switch and a test or dev system id, its scopes outside
  the catalogue. A deployment that wanted it would have to do all five
  on purpose (T11).
- The fixture operator uses `GEO-TEST-*` and `TEST*` values only; no
  production hostname, no secret in git.
