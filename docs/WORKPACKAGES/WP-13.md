## What to build

- `dss.Client`: the F3548 DSS operations over WP-3's client with an
  ecosystem token (`utm.strategic_coordination`, `utm.constraint_processing`,
  `aud` = the host of `USSP_DSS_BASE_URL`; peer calls use `aud` = the
  host of the peer's `uss_base_url`; reconciliation M18), deadlines, body caps, retry on 5xx with
  backoff, never on 4xx; a 409 `AirspaceConflictResponse` parsed into
  the missing ovns.
- Intent write protocol (`dss.Writer`, driven by `intent.v1` from WP-7
  through the `dss_outbox`): for an accepted intent inside U-space
  airspace (or anywhere, when `USSP_DSS_FOR_ALL=on`): query operational
  intent references and constraint references for the intent's
  extents; fetch each peer reference's details (`GET
  {uss_base_url}/uss/v1/operational_intents/{id}`, `trust: provider`,
  stored in `peer_intents`); run WP-7's `deconflict.Check` against them
  (a conflict here → the intent goes `rejected` with the peer reference
  named, or, if we are higher priority, proceeds and the peer is
  notified by the DSS flow); `PUT /dss/v1/operational_intent_references/{id}`
  with `key` = every ovn seen, `state Accepted`, `uss_base_url`, an
  implicit subscription; on 409 with missing ovns → refetch and retry
  once, then `pending_dss` with reason; on success store `ovn`,
  `version`, `subscription_id`, then `POST {subscriber}/uss/v1/operational_intents`
  to every subscriber the response lists with the details, within
  `UssOiChangeNotificationMaxSeconds` (5 s; a subscriber that fails is
  retried from the outbox and counted); a conflicting-intent
  notification (we displaced a lower-priority peer) within 1 s (Q16:
  attempted inline with a 900 ms deadline, else outbox + `peer_notify_late`).
  Activation, modification, `nonconforming`, `contingent` and end →
  the same `PUT` with the new state / `DELETE` with the ovn, and the
  same notifications. The DSS state written is only ever one of
  `f3548.DSSStates`; local states never leave (test asserts over every
  `local_state`).
- `dss.Subscriptions`: one `PUT /dss/v1/subscriptions/{id}` per
  configured area of interest (the U-space airspaces from `cis_current`
  plus `policy.PeerSubscriptionMarginM`), `notify_for_operational_intents`
  and `notify_for_constraints`, ≤ 24 h, renewed at 80 % of the window;
  the `notification_index` checked on every incoming notification
  (an index going backwards is counted and the notification applied
  anyway).
- USS endpoints in `api` (replacing WP-3's 501s): `GET
  /uss/v1/operational_intents/{entityid}` from the store within 1 s
  (details = our volumes as sent to the DSS, `off_nominal_volumes` when
  nonconforming, `priority`); `GET .../telemetry` (last position of a
  nonconforming/contingent flight from the TSDB window via `rid-sp`'s
  shape, scope `utm.conformance_monitoring_sa`); `POST
  /uss/v1/operational_intents` (peer notification: upsert `peer_intents`
  by `(entity_id, version)`, a deleted reference removes it, publish an
  internal `peer.intent.v1` for WP-12's console view and for WP-7's
  next decision); `POST /uss/v1/constraints` (upsert `constraints`,
  then call WP-12's `restriction_activated` path with the constraint's
  volumes and time; join to the CIS restriction by the ANSP reference
  when present in `details`); `POST /uss/v1/reports` (store, count);
  `GET /uss/v1/log_sets/{id}` (`USSLogSet` built from an exchange log
  this WP keeps: every DSS and peer request and response, bounded,
  7 days); `GET /uss/v1/constraints/{id}` → 404 problem (we manage
  none).
- `dss.Availability`: `GET /dss/v1/uss_availability/{our id}` every
  60 s → `dss_state`; `Down` set by the authority stops new DSS writes
  (intents go `pending_dss` with `uss_availability_down`) and is shown
  on the console; `Normal` resumes.
- Purge: `peer_intents` and `constraints` rows older than 24 h
  (`ExternalDataMaxRetentionTimeHours`) deleted every 10 min unless
  referenced by a decision record (`operational_intents.conflicts`
  copies what it relied on at decision time, so the purge never needs
  the row).
- `fakedss`: an in-memory DSS for tests implementing the operations we
  call with real `ovn`/`key` semantics (409 with missing ovns, version
  increments, subscriber lists) and a `Down()` switch; used by WP-9
  (ISA) and WP-14 too (extend it with the F3411 DSS operations if WP-9
  merged first with its own stub; one fake, not two).
- `/readyz` entry `dss` with reachability, availability, outbox depth
  and oldest item age.

## Safety notes

- The DSS is a broker, not an authority: a peer's intent is `trust:
  provider`; we never alter it and we never authorise over it. A
  conflict with a peer intent that the DSS let through is reported to
  the authority with evidence (an audit event with both references and
  the ovns) — the regulation handles the rest (T9).
- Clock: `TimeSyncMaxDifferentialSeconds = 5`; `/readyz` reports NTP
  drift when the host exposes it; a drift beyond 5 s is `degraded`.
- Nothing in this WP sends anything to an aircraft; a peer USS base URL
  is a USS, and the only calls to it are the standard's.
