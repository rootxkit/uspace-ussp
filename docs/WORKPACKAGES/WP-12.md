# WP-12: geo-awareness, zone alerts and standing re-check

Branch `feat/WP-12-geo-awareness`. Milestone S-M1 (`/v1/geo`), S-M4
(`restriction_activated` and the Art. 10(10) re-check). Owns
`internal/geo/`, the endpoints `GET /v1/geo` and `GET /v1/geo/intents/{id}`,
the geo change push on the traffic WS (a `geo_changed` frame), the zone
and identification kinds of `monitor`'s `alerting.Monitor` (`zone_incursion`,
`height_exceedance` mapping), the `restriction_activated` alert and the
standing-authorisation re-check (calls `intent`). Depends on WP-4
(`cis.Evaluator`), WP-7 (`intent`), WP-11 (`alerts`, the monitor's
events). Consumers: WP-17 (portal map), WP-13 (constraint intake
triggers the re-check).

Safety-relevant review (it withdraws authorisations); must pass the
N-M1/S-M4 restriction scenario in the lab before merge.

## What to build

- `GET /v1/geo?bbox=&at=` and `GET /v1/geo/intents/{id}` (scope
  `ussp.geo`; the intent's envelope and window as the query): the
  applicable U-space airspaces with their Art. 3(4) requirements,
  services required, adjacency; the geo-zones (ED-318 properties
  verbatim, limits with references, `limitedApplicability`) that apply
  at `at` or within the window; the restrictions with state and
  `starts_at`/`ends_at`; each item with `updated_at` (the publication's
  `updateDateTime`), `version` (dataset version), `valid_from/to`;
  envelope `cis_version`, `cis_age_s`, `stale` (beyond the bound).
  Response from the cache only; no CISP call in the request path.
- Geo change push: on `cis.v1.<dataset>` the traffic WS (WP-11's
  process; add a `geo_changed {dataset, version, feature_ids}` frame
  through a small hook interface this WP owns) tells subscribed
  operators to refetch.
- Zone kinds in `monitor`: for every track of an owned cell, `monitor`
  already runs `alerting.Monitor` with `Config.Zones` from `cis_current`
  (this WP wires the projection into the monitor's config and reloads it
  on `cis.v1` within one tick, Z-12) and `Env` from terrain/geoid
  lookups (`zones.Env{Ground, GroundM, UndulationM}`; no terrain →
  `GroundNotConfigured`). Map `Events` of kind `zone` → `alert/v1`
  `zone_incursion` (`zone_id`, `zone_type`, `vertical_known`,
  `limit_not_judged`, `within_band`, severity as the monitor says), kind
  `height` is **not** produced here (the 120 m rule is the authority's;
  `Config.ZonePolicy.MaxHeightAGLM` stays nil); `height_exceedance`
  against the authorised upper is WP-10's `above_upper` reason surfaced
  as its own kind for the operator UI (map it from `conf.v1`, not from
  core zones); kind `identification` / `identification_mismatch` →
  `alert/v1` with the same names (an unidentified or unknown-operator
  own flight is unlikely but a peer broadcast can be, G-03).
- `restriction_activated`: on a `cis.v1.restrictions` change or a
  constraint notification (WP-13 calls the same function), for every
  active intent (`intent_active`) whose envelope and window overlap the
  restriction → run `intent.Recheck(ctx, intentID, cause)` (WP-7's
  pipeline step 4 re-applied on the stored volumes): no overlap after
  the exact check → nothing; overlap → the intent is `withdrawn`
  (`change_reason: restriction <id>`) when it has not been activated, or
  marked for the operator with the restriction's window and
  `authorisation_updated: false, withdrawn: true` when activated and the
  overlap is in the future, and `nonconformance` is left to WP-10 when
  the aircraft is already inside the restriction; in every case an
  `alert/v1` `restriction_activated` (critical) with `restriction_id`,
  `affected_intents`, the decision; the operator's `intent/decision/v1`
  carries `change_reason` (Art. 6(6)); audit rows. Priority intents of a
  higher class displaced by a new special-operation intent (WP-7 step 5)
  go through the same `Recheck` with `cause: priority <intent id>`.
- Emergency manned aircraft (Art. 10(10) second limb): a `man.v1` track
  with `emergency: true` inside an intent's volume (now or within
  `policy.EmergencyLookaheadS`) → the same alert kind with
  `cause: manned_emergency` and no withdrawal (information to the
  operator; the ANSP's restriction is the regulatory channel). Shown on
  the console.

## Safety notes

- Withdrawing an authorisation tells a person; it does not stop an
  aircraft, and this WP must not try to (no message to the GCS beyond
  the decision and the alert).
- Zone severity comes from `core/zones.Severity`; a zone alert's severity
  is never raised above its restriction's (Z-10) and a U-space airspace
  boundary is information, not an incursion.
- The 120 m rule is not evaluated here. If a reviewer sees
  `MaxHeightAGLM` set in this repo, it is a scope error.
